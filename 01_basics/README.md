# 阶段一:编程模型与起步(初学者)

目标:理解 CUDA 的线程层次模型,能独立写出、编译并运行一个正确的 kernel;
初步建立"测量 → 定位 → 优化 → 复测"的性能分析习惯。

前置要求:会用命令行,有 C/C++ 基础(指针、数组、动态内存)。

预计用时:2~4 小时。

## 核心概念:编程模型

### 1. 线程层次:thread → block → grid

CUDA 把并行工作组织成三级:

- **thread**:最小执行单元,每个线程执行一遍 kernel 代码;
- **block**:一组线程,可通过共享内存通信、用 `__syncthreads()` 同步;
- **grid**:一次 kernel 启动的所有 block。

每个线程有唯一的内置坐标,据此算出自己负责的数据下标:

```c
int i = blockIdx.x * blockDim.x + threadIdx.x;   // 一维全局索引
```

二维问题(矩阵、图像)同理扩展到 `(row, col)`:

```c
int row = blockIdx.y * blockDim.y + threadIdx.y;
int col = blockIdx.x * blockDim.x + threadIdx.x;
// 行主序一维下标: idx = row * cols + col
```

约定:通常 **x → 列(宽)、y → 行(高)**。

### 2. kernel 启动与同步

一维(向量):

```c
kernel<<<grid_size, block_size>>>(参数...);
// block_size: 每 block 线程数,常用 128/256/512(宜为 32 的倍数)
// grid_size : block 数,向上取整 (N + block_size - 1) / block_size
```

kernel 启动是**异步**的:CPU 立即返回,需要 `cudaDeviceSynchronize()` 或后续
`cudaMemcpy` 隐式等待结果。

二维用 `dim3` 同时指定 x/y(未写的分量默认为 1):

```c
dim3 block(2, 2);   // blockDim.x=2, blockDim.y=2 → 每 block 2×2=4 线程
dim3 grid((cols + block.x - 1) / block.x,
          (rows + block.y - 1) / block.y);  // 覆盖 rows×cols
kernel<<<grid, block>>>(rows, cols);
```

例:`rows=cols=8`、`block(2,2)` → `grid` 为 `(4,4)`,共 16 个 block、
64 个线程,正好一线程对应一个 `(row,col)`。启动后仍要边界判断
`row < rows && col < cols`(grid 向上取整时边缘 block 可能越界)。

对照 `exercises/thread_grid_2d.cu` 练习二维坐标打印。

**显式同步放哪儿?** 不是"到处加",而是加在"需要看到结果的那一刻":

1. **host 要读 GPU 结果(或校验/打印 device 数据)时**——在读之前必须
   `cudaDeviceSynchronize()`。典型位置:kernel 里 printf 后想在 host
   继续(见练习 `hello_world.cu`)。
2. **检查启动错误时**——`CUDA_CHECK_LAUNCH()` 内部就是
   `cudaGetLastError()` + `cudaDeviceSynchronize()`,启动后紧接着调用,
   让异步的启动错误(如 grid/block 越界配置)当场暴露,而不是延迟到
   几百行之后。
3. **计时时**——event 计时必须 `cudaEventSynchronize(stop)` 之后才能
   `cudaEventElapsedTime`,否则读到的是"启动耗时"而非 kernel 执行耗时
   (见下文「观测方法:怎么拿到可信的数字」与 `vector_add.cu`)。

反过来,**后续紧跟阻塞式 CUDA 调用时不需要再手动同步**:`cudaMemcpy`
(阻塞流)、`cudaDeviceSynchronize`、event 同步自身都会等待前面的
kernel 完成。例如 `vector_add.cu` 的 kernel 之后直接 `cudaMemcpy` 拷回
校验即可,再 synchronize 是冗余的。

### 3. 错误检查

CUDA 的错误是静默的,不会抛异常。请从第一天起使用 `cuda_common.cuh` 里的
`CUDA_CHECK(...)` 包裹每个 API 调用,并在 kernel 启动后调用
`CUDA_CHECK_LAUNCH()`。

两个宏都把静默的错误码变成"当场报错退出",但检查的时机和对象不同:

- **`CUDA_CHECK(call)` 管 API 返回的错误码**。`cudaMalloc`、`cudaMemcpy`
  等运行时 API 都返回 `cudaError_t`,但 C 不会自动检查,错误会被静默
  吞掉;宏只是包一层:不是 `cudaSuccess` 就打印文件、行号、错误信息
  并退出,相当于其他语言里的 try/catch。
- **`CUDA_CHECK_LAUNCH()` 管 kernel 启动/执行错误**——kernel 启动语法
  `kernel<<<...>>>` 没有返回值,`CUDA_CHECK` 包不住它。它做两件事:
  1. `cudaGetLastError()`:取走启动时的**同步**错误(配置类,如 block
     超过 1024、共享内存超限,启动瞬间就知道);
  2. `cudaDeviceSynchronize()`:等 kernel 真正跑完,把**异步执行**错误
     (如越界访存)也暴露出来——这类错误默认滞留到下一次 CUDA 调用
     才报,不主动同步的话,报错位置会漂移到几百行之后,极难定位。

注意 `CUDA_CHECK_LAUNCH` 里的 synchronize 有额外开销:调试阶段每个
kernel 启动后都调用;确认正确后、只做性能测量时,可只保留
`cudaGetLastError()`。

## 硬件执行模型:grid/block 如何落到 SM

这一节回答"写好的 kernel 在硬件上是怎么跑的"。它既是理解性能的基础,
也是后面性能分析方法的理论底座。先跑 `make run T=device_info`,
对照本机 RTX 3060 的输出:

```text
=== Device 0: NVIDIA GeForce RTX 3060 ===
  Compute capability : 8.6
  SM count           : 28
  Max threads/SM     : 1536      ← 48 个 warp 槽位(1536 / 32)
  Max threads/block  : 1024
  Shared mem/block   : 48.0 KB
  Warp size          : 32
  Max blocks/SM      : 16        ← cudaDevAttrMaxBlocksPerMultiprocessor
```

### 1. SM 内部:1536 个线程落在哪些计算单元上

一个 SM 不是一块"大核",而是一组计算资源的集合。RTX 3060(Ampere)
每个 SM 内部:

```text
SM(共 28 个)
├── 128 个 FP32 CUDA core,分成 4 个处理子块(各 32 个)
│   └── 每子块配 1 个 warp 调度器 + 1 个指令分发单元
├── 寄存器堆:64K 个 32-bit 寄存器(全 SM 共享)
├── 共享内存 / L1 缓存:共 128 KB(block 可配置用最多 48 KB)
└── 纹理/缓存单元
```

#### warp:硬件调度的最小单位

关键中间层是 **warp**:硬件把 block 的线程按**线性 thread id 切分**,
每 32 个连续线程组成一个 warp —— warp 才是硬件调度的最小单位。
x 分量变化最快,所以一维 block 就是 `tid 0-31` 为 warp 0、`32-63` 为
warp 1……三维 block 先按 x 展开、再 y、再 z(详见 Programming Guide
§2.4 的线性化公式)。同一 warp 的 32 线程**锁步**执行同一条指令
(SIMT),这正是阶段四讲 warp divergence 和 warp shuffle 的根源。

"1536 threads/SM" 因此不是 1536 个线程各占一个 core,而是 **48 个 warp
槽位**:4 个 warp 调度器各管 `48 / 4 = 12` 个 warp,从自己子块的 32 个
core 里挑可发射的指令。某个 warp 遇到访存等待时,其调度器零开销切换到
同子块另外 11 个 warp 中就绪的那个 —— 这就是"用大量线程掩盖内存延迟"
的机制(12 个 warp 竞争 32 个 core,恰好保证 core 始终有活干)。

warp 编号 w0..w47 的归属:硬件按 **warp_id % 4** 轮转分配到 4 个调度器,
所以 w0/w4/w8/… 在调度器 0 —— 同一 block 的 warp(连续编号)自然
被摊到不同调度器上。

调度器与子块的对应关系,以满载(4 个子块各驻留 12 个 warp)为例:

```text
SM 内部的 4 个处理子块(每个完全对称,互不干涉):

  子块 0               子块 1               子块 2               子块 3
┌─────────────┐   ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│ 调度器 0     │   │ 调度器 1     │   │ 调度器 2     │   │ 调度器 3     │
│ 管 12 warp: │   │ 管 12 warp: │   │ 管 12 warp: │   │ 管 12 warp: │
│ w0 w4 w8..  │   │ w1 w5 w9..  │   │ w2 w6 w10.. │   │ w3 w7 w11.. │
│  ↓ 每周期   │   │  ↓ 每周期   │   │  ↓ 每周期   │   │  ↓ 每周期   │
│  择 1 发射  │   │  择 1 发射  │   │  择 1 发射  │   │  择 1 发射  │
├─────────────┤   ├─────────────┤   ├─────────────┤   ├─────────────┤
│ 32 FP32 core│   │ 32 FP32 core│   │ 32 FP32 core│   │ 32 FP32 core│
│ 16 LD/ST    │   │ 16 LD/ST    │   │ 16 LD/ST    │   │ 16 LD/ST    │
│ 16 SFU      │   │ 16 SFU      │   │ 16 SFU      │   │ 16 SFU      │
└──────┬──────┘   └──────┬──────┘   └──────┬──────┘   └──────┬──────┘
       │  执行单元:子块私有,只服务本子块的 warp,互不竞争  │
┌──────┴─────────────────┴─────────────────┴─────────────────┴──────┐
│ SM 级共享(4 个子块竞争,同 SM 的 block 互相挤压):                 │
│   寄存器堆 64K × 32-bit(驻留 warp 的寄存器从这里划拨)             │
│   共享内存 / L1 128 KB(驻留 block 按申请切块)                     │
└───────────────────────────────┬───────────────────────────────────┘
                                │ 4 个子块的访存请求在此汇入
┌───────────────────────────────┴───────────────────────────────────┐
│ GPU 级共享(全部 28 个 SM 竞争,全局竞争的主战场):                 │
│   L2 缓存 ─── 显存控制器 ─── DRAM                                  │
└───────────────────────────────────────────────────────────────────┘
```

#### 调度器与指令分发单元:一对搭档

"4 个 warp 调度器 + 4 个指令分发单元"来自 CUDA Programming Guide
硬件附录按算力列的表格(CC 8.6 即此配置),两者是紧密咬合的 1:1 搭档,
共同完成"每周期发射一条 warp 指令",但分工不同:

- **warp 调度器 = 做决策的那级**:每周期扫一遍自己管的 12 个驻留
  warp,挑出一个"就绪"的(指令已译码、操作数不缺、没卡在 barrier/
  访存等待)。它只回答"这周期发谁的指令"。
- **指令分发单元 = 干活的那级**:把选中的 warp 指令驱动到正确的
  执行端口(FP32 core、LD/ST、SFU),解决"送到哪排 core 上"。

即调度器选 warp,分发单元送指令。之所以必须成对出现:一个分发单元
每周期只能送一条指令,4 个调度器要各自满速工作(合计每周期 4 条
warp 指令、理论 4 IPC),就得配 4 个分发单元一一对应——所以硬件表
里这两个数字永远相等,少一个就会在那一子块形成发射瓶颈。

#### 三类执行单元

三层资源的归属规则:**执行端口(FP32 core、LD/ST、SFU)子块私有**,
warp 发散只浪费自己子块的 core;**寄存器堆和共享内存/L1 是 SM 级**,
同 SM 上逻辑无关的 block 也通过它们互相挤压;**L2 及以下是 GPU 级**,
28 个 SM 的所有访存最终都在这里排队。

- **FP32 core(每子块 32 个)**:执行普通算术/逻辑指令——加减乘、
  乘加 FMA、比较、位运算等。这是数量最多、通用的主力单元,一条
  warp 指令(32 线程)正好一拍铺满 32 个 core。
- **LD/ST 单元(每子块 16 个)**:执行访存指令——全局内存/共享内存的
  读取与写入、寄存器与显存之间的搬运。它本身不是缓存,而是"搬运工":
  发出地址、拆分对齐的访存请求、把数据送回寄存器堆。因为带宽只有
  FP32 core 的一半(16 vs 32),访存密集的 kernel 常在这里排队。

  三点细节:

  1. **是每子块 16 个,不是全 SM 共 16 个**——4 个子块各有一套,
     32 FP32 : 16 LD/ST 的 2:1 配比是有意设计。访存指令的粒度是
     "一条 warp 指令":32 个地址由 16 个单元消化,一条 warp 访存
     占 2 拍,而 FP32 指令 1 拍铺满——访存指令的发射"单价"天然是
     算术指令的 2 倍;
  2. **LD/ST 是一个物理单元**,不是 LD 一套、ST 一套。"LD/ST" 只是
     职责描述(既能 load 也能 store),同一端口两种指令都过,共享
     同一份吞吐配额——load 和 store 密集时在同一组端口上互相排队。
     硬件附录也只列一个数(如 CC 8.6 每子块 16 LSU),不分开计;
  3. **"数量不足"不会直接卡住 FP32 core**。warp 发出 load 后进入
     停等,调度器立刻切到别的就绪 warp 继续发 FP32——前提是有足够
     多的驻留 warp 可切(否则延迟裸露,core 空转,见「性能分析入门」
     的占用率分析)。LD/ST 吞吐真正饱和的场景是共享内存密集或
     寄存器溢出(spill)大量走 local memory 的 kernel;全局内存
     kernel 几乎总是先撞上 DRAM 带宽(L2 以下那层)。非合并访存会
     雪上加霜:32 个地址若散落在不同扇区,LSU 要拆成多次事务,
     占用单元的拍数成倍增加。Nsight Compute 里可观察 LSU 管线
     利用率确认;缓解手段:向量化加载(`float4` 一条指令搬 4 个数)、
     消除溢出、合并访存。
- **SFU(Special Function Unit,每子块 16 个)**:执行超越函数——
  `sin`/`cos`、`exp`/`log`、`rsqrt`/`sqrt`、常用插值等,用查表+插值的
  硬件近似实现(几拍出结果)。`__sinf()` 这类快速内建函数走 SFU;
  而双精度或要求精确舍入的 `sinf()` 则退化成多拍软件序列,慢得多。

### 2. 4 个调度器之间如何"竞争"

先把结论说反直觉:调度器彼此之间**几乎不竞争** —— 每个 warp 归属
唯一的调度器,warp 不会在调度器之间流动,每个调度器也只往自己子块的
32 个 core 发射指令。调度器每周期从自己管的 12 个 warp 里挑一个就绪
的发射(择一而发),4 个调度器**并行工作、互不干涉**,最多每周期发射
4 条 warp 指令。它们像一个车间的 4 个组长:每人带 12 个工人,各管各的,
不存在抢工人的问题。

真正的竞争发生在**下游共享资源**上,这才是值得关注的:

- **执行端口**:32 个 FP32 core 是子块私有的,但每子块只有 16 个
  LD/ST(访存)单元和 16 个 SFU(特殊函数)单元 —— 一个子块
  12 个 warp 若同时发访存指令,得排队,吞吐量被摊薄;
- **寄存器堆**:64K 个寄存器全 SM 共享。A 的 warp 用寄存器越狠,
  B、C、D 的调度器可驻留的 warp 就越少 —— 这直接压低全 SM 占用率,
  是阶段四 `occupancy.cu` 里"寄存器压力"的来源;
- **共享内存/L1**:128 KB 全 SM 共享,block 之间按申请切块
  ——但"切块"受一组具体约束(本机 CC 8.6 实测):

  1. **总量拆分:L1 固定 28 KB,共享内存上限 100 KB**。CC 8.6 与
     其他算力不同,L1 和共享内存的分割线是固定的,不能把 L1 让给
     共享内存;100 KB 即 `sharedMemPerMultiprocessor`(每 SM 上
     **所有驻留 block 的共享内存之和**不得超过它);
  2. **单个 block 默认上限 48 KB**(`sharedMemPerBlock`),不用任何
     设置就能申请的量。要超过它必须显式 opt-in:
     `cudaFuncSetAttribute(kernel, cudaFuncAttributeMaxDynamicSharedMemorySize, ...)`,
     上限是 99 KB(`sharedMemPerBlockOptin`,被每 block 1 KB 的
     保留扣掉了 1 KB);
  3. **占用率约束**:block 之间按申请切块,意味着同一 SM 上的
     block 互相挤压——比如每 block 申请 20 KB,则 100/20 = 最多
     驻留 5 个 block(还没到 warp 槽位上限);申请 34 KB 则每 SM
     只能住 2 个。这也是阶段四 `occupancy.cu` 里"共享内存压力"
     的来源;
  4. **过时认知**:网上常见"CC 8.x 的 L1/共享内存 carveout 可配置
     (0%/50%/100% …)"说的是 CC 8.0(A100,192 KB 池),8.6 这类
     消费级芯片 carveout 是**固定的**,`PreferredSharedMemoryCarveout`
     设了也不改变 28+100 的分界。
- **SM 级缓存与 DRAM 带宽**:4 个子块的访存请求最终汇入同一个 L2/
  显存通道,这里才是全局竞争的主战场。

所以调优视角是:同一 SM 上的 4 个子块靠共享寄存器堆和内存系统互相
影响,而不靠调度器抢占。这也解释了两个常见现象 ——
① warp 发散只浪费自己 warp 的 core,不拖累其他调度器的 warp;
② 一个 block 的寄存器用量会"挤压同 SM 邻居"的驻留数量,哪怕它们
逻辑上毫无关系。

### 3. block 与 SM 的关系:整体驻留,不可拆分

- **一个 block 只会落在一个 SM 上**,其线程、共享内存、同步关系
  (`__syncthreads`)都在该 SM 内部完成 —— 这是"block 内可协作、
  block 间只能靠原子/全局内存"的硬件原因;
- **一个 SM 可以同时驻留多个 block**(直到 48 个 warp 槽位、寄存器、
  共享内存任一资源耗尽);
- block 一旦驻留就**跑完才退出**,中途不迁移。

分配由启动时的 **GigaThread 引擎(工作分发器)**完成:grid 里全部
block 排队,只要某 SM 有空闲槽位(整 block 的 warp 数 + 寄存器 +
共享内存都能放下),就派一个 block 过去,如此滚动直到 block 派完。

注意"整体驻留"是**驻留在 SM 级别**,不是驻留在单个调度器级别:
block 的 warp 会按**轮转方式铺到 4 个调度器**上 —— 256 线程 block 的
warp 0/4/8/… 归调度器 0,warp 1/5/9/… 归调度器 1,依此类推。于是每个
调度器从该 block 拿到 2 个 warp。也就是说:**同一 block 的线程确实由
不同调度器调度**,但它们仍在同一个 SM 内,共享内存和 `__syncthreads()`
照常工作 —— 协作性是 SM 级的,不是调度器级的。

### 4. 落到本机数字:vector_add 的分配过程

```c
const int N = 1 << 24;
const int block_size = 256;                       // → 8 个 warp/block
const int grid_size = (N + block_size - 1) / block_size;   // 65536 个 block
vector_add_one_per_thread<<<grid_size, block_size>>>(...);
```

驻留容量:每 block 8 warp,SM 有 48 个 warp 槽位 → 槽位角度可放
`48/8 = 6` 个 block;再查寄存器(kernel 每线程用量很小)、共享内存
(此 kernel 为 0)都够 → 每个同时驻留 6 个 block(48 warp 满载,
即"占用率 100%")。这不是估算 —— 本机用 occupancy API 实测该 kernel
确实返回 6 blocks/SM,而 1024 线程的大 block kernel 只返回 1
(`48/32 = 1.5` 取整),印证了上述公式。

6 个 block × 每 block 8 warp,轮转分给 4 个调度器:每调度器
12 个 warp,与 `48/4 = 12` 正好吻合。

于是执行过程是:28 个 SM × 6 block = 168 个 block 先驻留,其余
65536 − 168 ≈ 65368 个 block 在队列里等;某 SM 的一个 block 跑完退出,
分发器立刻补一个进去 —— **grid 不是一次性塞进 GPU 的,而是流水般
滚动消化**。这也是为什么 grid 可以远超 GPU 容量(6.5 万个 block、
1600 万线程都完全没问题)。

滚动消化的过程:

```text
时刻 T0:grid 里 65536 个 block 排队

 GigaThread ──派发──▶  SM0[6块] SM1[6块] ... SM27[6块]   ← 驻留 168 块
      │
      │  SM3 的某个 block 跑完退出 → 腾出 8 个 warp 槽
      ↓
时刻 T1:分发器立即从队列取 1 块补进 SM3           ← 队列 65536-168 → 65367
      ↓
      ……直到队列排空。全程每个 SM 始终保持 6 块驻留(占用率 100%)
```

一图总结三层映射:

```text
grid(65536 blocks)                    ← 逻辑:一次 kernel 全部工作
   └─ GigaThread 分发器按容量滚动派发
        └─ SM(28 个,每个驻留 ≤6 个 256 线程 block)
             └─ block 整体驻留,共享内存/同步封闭在内
                  └─ 8 个 warp(硬件调度单位,32 线程锁步)
                       └─ 4 个调度器各管 12 个 warp,等待时切换掩盖延迟
                            └─ 32 个 CUDA core 执行指令
```

## 性能分析入门:以 vector_add 的四组实验为样本

写完 kernel 只是第一步,知道它"为什么快/慢"才是 CUDA 工程能力。
这一节用 `vector_add.cu` 里现成的四组实验,演示完整的分析套路:
**从观测出发 → 算出瓶颈指标 → 定位根因 → 得出普适结论**。

### 1. 分析角度:先问"这个 kernel 在等什么"

任何 kernel 的耗时都由两类资源中"更慢的那个"决定:

| 瓶颈类型 | 特征 | 典型症状 |
|----------|------|----------|
| **带宽受限**(bandwidth-bound) | 数据量大、每个字节的计算少 | 加带宽利用率已接近上限,堆线程无用 |
| **延迟受限**(latency-bound) | 驻留的 warp 不够,掩盖不了访存等待 | 提高占用率(更多 warp)直接提速 |

vector_add 每元素只做 1 次加法、搬 12 字节(读 x、y 各 4 字节 +
写 out 4 字节),是极端的带宽受限问题;但 block 太小时它会"降级"
为延迟受限 —— 这正是四组实验展示的东西。

### 2. 观测方法:怎么拿到可信的数字

**测耗时**:用 `cudaEvent`(不是 host 的 clock,kernel 是异步的):

```c
cudaEventRecord(start);
kernel<<<grid, block>>>(...);
cudaEventRecord(stop);
cudaEventSynchronize(stop);        // 必须同步,否则读到的是启动耗时
cudaEventElapsedTime(&ms, start, stop);
```

三条观测纪律(本模块所有实验数据都遵守):

1. **预热一次再测**(排除首次启动的 context/模块加载开销);
2. **多次取平均**(单次有 ±5% 噪声;结论差异小于噪声就是"没有差异");
3. **只测 kernel 本身**:event 包住的范围不含 H2D/D2H 传输,
   传输耗时用 nsys 单独看(`make profile T=vector_add`)。

**观测驻留上限**:`device_info` 打印的 `Max blocks/SM`(16)与
`Max threads/SM`(1536)就是占用率的两个天花板;精确到某个 kernel
用 occupancy API:

```c
int blocks;
cudaOccupancyMaxActiveBlocksPerMultiprocessor(&blocks, kernel, block_size, 0);
```

### 3. 计算方法:把耗时换算成瓶颈指标

裸的毫秒数看不出问题,要换算成**利用率**。三个必会公式:

```text
有效带宽 (GB/s) = 显存流量 (字节) / 耗时 (s) / 1e9
                    vector_add: 3 × N × 4 字节(读 x/y + 写 out)

占用率 (%)       = 驻留 warp 数 / 48

有效驻留线程/SM  = min(驻留 block 数, 16) × block_size   ← 粗估
```

四组实验换算后的完整对照(N=2^24,流量 = 3×N×4 字节 ≈ 201MB):

| 组 | block | 驻留 block/SM | 限制因素 | warp 槽位利用 | 有效带宽 | 带宽利用率 | 耗时 |
|----|-------|--------------|----------|---------------|----------|-----------|------|
| 1 | 256 | 6 | 线程上限(48 warp) | 100% | ~320 GB/s | 96% | 0.63 ms |
| 2 | 16 | 16 | **block 上限(16)** | 33% | ~102 GB/s | 31% | 1.98 ms |
| 3 | 33 | 16 | block 上限(16) | 67%(碎片) | ~246 GB/s | 74% | 0.82 ms |
| 4 | 48 | 16 | block 上限(16) | 67%(碎片) | ~310 GB/s | 93% | 0.65 ms |

把 block 从 16 扫到 256(结合 04_optimize/occupancy.cu 的数据),曲线
形状一目了然:

```text
有效带宽 (GB/s)
332 ┤                         ┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄  可达带宽上限(332,coalesce 实测)
    │                     ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓ ← 饱和平台期(93~99%)
320 ┤              ▓▓▓▓▓▓▓ (256)
310 ┤         ▓▓▓▓▓ (48)
    │        ▓ (64: 330)
246 ┤      ▓ (33)
    │     ▓
102 ┤ ▓▓▓▓ (16)
    └─┬────┬────┬────┬────┬────┬────┬──
     16   33   48   64   96  128  256   block 线程数
      ↑延迟受限区(加线程直接提速)↑   ↑带宽饱和区(加线程无用)
```

曲线三段式,对应三种状态:**陡坡**(延迟受限,驻留 warp 不足以掩盖
访存等待,加线程直接换带宽)→ **膝点**(64 附近,延迟已被掩盖)→
**平台**(带宽饱和,瓶颈转移到 DRAM,与占用率解耦)。调优就是找膝点;
平台期继续堆线程只是让请求在队列里排队。

### 4. 根因定位:三个层层递进的结论

1. **block 太小 → 撞 16-block 上限**(组 2):每 block 只有 1 warp,
   16-block 上限让每 SM 最多驻留 16 warp,48 槽位空 2/3,
   掩盖访存延迟的 warp 不够 → 3 倍慢。这是"延迟受限"的教科书案例;

   ```text
   组 2(block=16)的 SM 槽位占用:          组 1(block=256):
   ┌──────────────────────────┐            ┌──────────────────────────┐
   │ █ █ █ █ █ █ █ █ █ █ █ █  │ 16 warp    │ ████████████████████████ │
   │ ░ ░ ░ ░ ░ ░ ░ ░ ░ ░ ░ ░  │            │ ████████████████████████ │
   │ ░ ░ ░ ░ ░ ░ ░ ░ ░ ░ ░ ░  │            │ ████████████████████████ │
   │ ░ ░ ░ ░ ░ ░ ░ ░ ░ ░ ░ ░  │ 32 空槽    │ ████████████████████████ │
   └──────────────────────────┘            └──────────────────────────┘
     ██=就绪 warp  ░=空槽                     48 warp 满载
   调度器想切却没 warp 可切 → 延迟裸露        → 延迟被充分掩盖
   ```

2. **block 个数相同 ≠ 性能相同**(组 3 vs 组 4):33 和 48 线程的
   block 驻留数一样(16 个),耗时差 25%。差异在 warp 碎片:
   33 线程切 2 个 warp 只用 33/64 = 52% 槽位(第二个 warp 只干
   1/32 的活),48 线程用 75%。**比的是每 SM 有效驻留线程
   528 vs 768**,不是 block 数;

   ```text
   组 3(block=33,2 个 warp/块)的槽位明细:

   warp 0: [t0 t1 ... t31        ] 32 线程全在干活
   warp 1: [t32                   ] 只有 1 个线程!31 个空转
            ↑ 33 = 32 + 1,碎片就碎在这里

   每 SM:16 block × 2 warp = 32 个 warp 槽,其中
   有效线程 16×33 = 528,槽位却占 32×32 = 1024 → 一半的槽位在陪跑
   ```

3. **占用率有边际收益封顶**:64 线程(67% 槽位)就能跑到
   ~330 GB/s ≈ 可达带宽的 99%,96/128/256 全部停在 0.60ms 平台期 ——
   带宽已饱和,**性能由瓶颈资源决定,与占用率解耦**,再堆线程只是
   让访存请求排队。

由 2、3 直接得到实用规则:**block 尺寸应为 32 的倍数**(消灭碎片),
**常用 128/256/512**(都能满载,且够大以压住 16-block 上限)。

### 5. 分析方法的普适流程

把上面的过程抽象成以后每个 kernel 都可以走的决策流程:

```text
                    ┌─────────────────────────────────┐
                    │ ① 测 kernel 耗时                 │
                    │   cudaEvent + 预热 + 多次平均    │
                    └────────────────┬────────────────┘
                                     ↓
                    ┌─────────────────────────────────┐
                    │ ② 算有效带宽                     │
                    │   流量/耗时,对比可达带宽         │
                    │   (3060 ≈ 332 GB/s)             │
                    └────────────────┬────────────────┘
                                     ↓
                        ┌───── 利用率 ≥ 90% ? ─────┐
                       是│                          │否
                        ↓                          ↓
        ┌───────────────────────────┐  ┌─────────────────────────────┐
        │ 带宽饱和(bandwidth-bound) │  │ 延迟受限(latency-bound)    │
        │ 性能与占用率解耦          │  │ 按序排查 ↓                  │
        │ 想更快只能:              │  │ ┌─────────────────────────┐ │
        │  · 少搬数据(压缩/融合)  │  │ │③ 占用率:驻留 warp ≥32? │ │
        │  · 提访问合并度          │  │ │  短板 = 16-block 上限 /  │ │
        │  · 换算法                │  │ │  寄存器 / 共享内存?     │ │
        └───────────────────────────┘  │ └───────────┬─────────────┘ │
                                       │             ↓ 修完复测      │
                                       │ ┌─────────────────────────┐ │
                                       │ │④ 访存合并:连续地址?    │ │
                                       │ │  (阶段四 coalesce.cu)   │ │
                                       │ └───────────┬─────────────┘ │
                                       │             ↓               │
                                       │ ┌─────────────────────────┐ │
                                       │ │⑤ 分支发散:warp 走两条   │ │
                                       │ │  路径?(divergence.cu)  │ │
                                       │ └───────────┬─────────────┘ │
                                       │             ↓               │
                                       │      回到 ② 重新计算        │
                                       └─────────────────────────────┘
```

要点:**每次只改一个变量,改完立刻回到第 ② 步复测** —— 优化是闭环,
不是一次性清单。

工具进阶:event 计时只能回答"多快",回答"为什么"需要 profiler:
`make profile T=<名>`(nsys,时间线/kernel 汇总)和 `ncu`(kernel 内部
指标,如带宽利用率、占用率、发散度)—— 见阶段四详解。本节的手工
计算是 profiler 指标的"人肉版",先会算,再看懂工具输出。
